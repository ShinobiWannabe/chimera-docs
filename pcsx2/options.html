Options

Settings the PCSX2 core exposes in the New Project wizard. Click a column heading to sort. Click again to reverse. Settings that are identical on every machine are listed once.

Machineps2, system246, system256, system256superps2Which of this package's machines the project is. 'ps2' is the PlayStation 2 console. The other three are NAMCO's arcade boards. These ARE PlayStation 2s: a Sony COH-H motherboard with a NAMCO board in the expansion bay. They need a different kind of project. It has an arcade BIOS from a COH-H board and not a retail one, the game's security dongle, its media and a boot program, each as a file of its own kind, and it has a JVS control panel in place of the controller ports. 'system246' runs the main processor (the EE) at the console's 294.912 MHz. 'system256' runs it a third faster (393.216 MHz) and 'system256super' a half faster (442.368 MHz). The clock speed is the difference between those two boards, and a game recorded on one does not play back on the other. The machine decides the whole project: its inputs, its files, its settings and its firmware. A movie made on one machine does not run on another.

Log the Machinetrue, falsefalseMakes PCSX2 report what it is doing on the standard error output: which BIOS and disc it found, what the input/output processor (the IOP) loaded, and what it refused. It does not change the machine, because the clock this core runs on is the emulated console's and does not depend on who reads the log. It is the first thing to turn on when a project will not start.
CPU Coresrecompiler, interpreterrecompilerWhich processor implementations run the machine. The recompilers translate the code of the EE, the IOP and both VUs to x86 code as it runs. This is how PCSX2 itself normally plays, and it is several times faster. The interpreters execute every instruction one at a time, which is the slowest and most literal way. They are DIFFERENT MACHINES, because the recompiler's EE floating point does not give the same results as the interpreter's. So the project and the movie record the choice, and a movie made with one does not play back with the other.
Renderersoftware, opengl, opengl-hw, vulkan-hwsoftwareWhich renderer draws the picture. 'software' is PCSX2's own software renderer and the default. It runs completely inside the core on the processor, so the picture is the same on every computer that plays the movie and does not depend on your graphics driver. Two runs of 2401 frames of Gran Turismo 4 with it are identical byte for byte at frames 900, 1500 and 2400. 'opengl' is PCSX2's OpenGL renderer, the one PCSX2's developers test with and most games are checked with. Here it draws with an OpenGL that is built into the core (Mesa's softpipe). It also gives the same picture on every computer, and it is slower than the software renderer. 'opengl-hw' is the same OpenGL renderer drawing on your computer's graphics card. It and 'vulkan-hw' are the fastest where there is a graphics card: the same 2401 frames took 9.6 seconds on a GTX 1060, against 20.6 seconds with the software renderer. It does NOT give the same picture everywhere. The picture comes from a driver that is outside the core and outside the savestate, and it differs between computers. A movie recorded with it records that a graphics card drew the picture. It is not the default because it is the choice that has gone wrong in use. The picture of a run that was recorded again could come back visibly wrong (ToolAssisted-run/chimera issues 55 and 56). And when a build or a computer cannot give it OpenGL, it falls back to the softpipe, which on Windows crashes after about a thousand frames. 'vulkan-hw' is PCSX2's Vulkan renderer drawing on your computer's graphics card. What is said of 'opengl-hw' is true of it: the picture comes from a driver outside the core, it differs between computers, and a movie recorded with it records that a graphics card drew the picture. On a GTX 1060 it is as fast as 'opengl-hw': 3700 frames of Street Fighter EX3 took 13.6 seconds with it and 13.8 seconds with 'opengl-hw', and the last picture was the same. It has nothing to fall back on. It needs a graphics driver that has Vulkan and a Chimera that hands Vulkan to cores, and without either the project does not start and says why. No renderer changes the machine: the console's main memory after 2401 frames is identical with the software renderer and with the graphics card. So the choice is about the picture and the speed, and never about the run.
Deinterlacingauto, adaptive, adaptive-bff, weave, weave-bff, blend, bob, offautoHow the console's two fields become one picture, when the game produces fields at all. In an interlaced mode a PS2 sends out HALF a picture per frame: 224 lines of 448, with the other half in the next frame. Something has to decide what a single field looks like as a whole frame. But many games draw WHOLE frames instead, and running one of those through a deinterlacer destroys half of it: the picture then always has one row from this frame and one row from the previous frame. 'auto' asks the machine which of the two it is doing. It leaves a whole frame alone and rebuilds a field picture with 'adaptive'. This is what PCSX2 itself does, and it should normally be left on. The other choices force one method. 'adaptive' compares this field with the three before it and decides for each pixel whether to keep a line or to make one from the lines above and below. Still pictures keep their full detail, and moving ones show no comb pattern. 'weave' puts each field's lines back in their proper places. That is the full picture the television showed, and fast motion shows a comb pattern, as it does on the real machine. 'weave-bff' and 'adaptive-bff' are the same with the order of the fields swapped, for a game that looks one line out of place. 'blend' is weave with the comb pattern softened. 'bob' shows the current field alone, scaled up. It never shows a comb pattern, and it has half the vertical detail. 'off' hands over the field stretched and places nothing, which makes a still screen move up two lines and back down on every frame.
Texture Filteringmachine, nearest, linear, linearNoSpritesmachineHow a texture is sampled when one texture pixel does not land on exactly one screen pixel. It applies to the OpenGL and Vulkan renderers only. The software renderer samples the way the console's graphics chip (the GS) does and ignores this. 'machine' is what the game asked the GS for, texture by texture, and gives the picture the console drew. 'nearest' always takes the nearest texture pixel. 'linear' always blends, which smooths a game that asked for nearest. 'linearNoSprites' does the same but leaves sprites alone, which keeps 2D text sharp. THIS SETTING CAN AFFECT WHETHER A MOVIE PLAYS BACK. It decides what the graphics card puts into every surface it draws, and PCSX2 writes such a surface back into the console's memory whenever a game reads its own picture. For such a game, the bytes it reads depend on this value. When measured on Maximo and Gran Turismo 4 (up to 6000 frames) it changed the picture and not one byte of memory. The project records it all the same, and a movie made with one value needs the same value to play back. Choose it when the project is created.
FXAAtrue, falsefalsePCSX2's own fast approximate anti-aliasing (FXAA). It is a shader that runs over the finished picture, after the console's display circuits have combined it. It applies to the OpenGL and Vulkan renderers only. The software renderer has no shader stage, so there it stays off whatever is chosen here. Nothing reads the finished picture back, so this cannot change the machine. When measured on Maximo, Gran Turismo 4 and Street Fighter EX3 it changed the picture and not one byte of memory, the audio or the lag count. It is a project setting because that is the only way a value reaches a core, and because it is how the movie's picture looked. A movie made with it plays back without it, and the other way round. Changing it restarts the core, as changing any setting does.
Internal Resolution1x, 2x, 3x, 4x1xPCSX2's own upscaling. Every surface is drawn at this multiple of the console's size, so 3D looks sharper and a video can be made at a higher resolution. It applies to the OpenGL and Vulkan renderers only. The software renderer draws at the console's own size and ignores this. It works best with 'opengl-hw', because an OpenGL without a graphics card pays for every extra pixel on the processor. THIS SETTING CAN AFFECT WHETHER A MOVIE PLAYS BACK, in the same way as Texture Filtering. A game that reads its own picture back gets it through PCSX2's texture cache, which scales an upscaled surface back down, and the result is not always byte for byte the picture at the console's size. The project records it, and a movie made with one value needs the same value to play back. 2D games gain little, and some show seams at 2x and above, as they do in PCSX2.

A PS2 cannot run a single instruction without its BIOS, and the emulator has no built-in replacement for it. The BIOS decides the console's region, its language, its menus, and what a game checks when it refuses to run. Each choice expects one exact file. The firmware page names the file and the SHA-1 it must have. Two projects with different BIOS versions are different machines and cannot share movies. The retail consoles are listed first. After them come the ROMs of the development kits (DEVKIT) and debug stations. Last comes the DVD PLAYER firmware, which is the ROM of the disc player and not a boot ROM, so a machine does not start from it.
Boot ROM (NAMCO System 246)coh-h-246c, coh-h-a000010coh-h-246cWHICH arcade board this project is, in the only way the hardware can be told apart. Sony never changed the version or the date in a COH-H ROM: every one says v1.00 (2000-03-06). So the EXTINFO build serial inside the file is what tells them apart, and it names the board. 20021119-163841 is a System 246 Rack C. 20040519-145634 is a System 256 (the Super 256 runs the same ROM with a faster bus clock). 20000901-114731 is the COH-H A-000-010 development board. 'coh-h-256-mirrored' is the same System 256 ROM as a 4 MB file with its two megabytes written twice, which some copying tools produce. It is offered because that file is in circulation, and this core accepts firmware only by its exact hash. A RETAIL PlayStation 2 BIOS does not work and is not offered here. The arcade boot software differs in many module interfaces, and an arcade game does not run on a retail BIOS. The firmware page names the file and the SHA-1 it must have.
Game IDAny textNAMCO's part number for this game: "NM" and five digits, such as NM00004 for Tekken 4, NM00007 for Soul Calibur II and NM00019 for Tekken 5. It identifies the game the way a MAME set name does. The JVS board (the cabinet's input board) reads it to know how this cabinet's control panel was wired: which switch is which button, whether there is a wheel, a drum or a pair of levers, and where a light gun's sensor reports. A project that leaves it empty gets the board's general wiring. That starts and can be played, but it is not the cabinet the game was made for.
Mediacd, dvd, hdddvdThe kind of medium the game was supplied on. It decides how the board's own disk controller (ATA/ATAPI) reads it. A COH-H board has no disc drive of its own, so the media is in the NAMCO board's drive and not in the console's tray. The exception is a CD game, which also asks the console for the disc, so this core puts it in both places. You choose the kind here, and it is not guessed. The PCSX2 version that this board support comes from looks it up in a game database, but a project states its own settings.
Board RAM (NAMCO System 246)0, 32, 64, 12864How much memory the cabinet has on the NAMCO board, in megabytes. A System 246 Rack A takes expansion boards of 32 or 64 MB in two slots. Racks B and C have 64 MB built in. Wangan Midnight's cabinet has 128. A System 256 has none, and should be set to 0. It is a setting, and is not guessed from the game, for two reasons. The board's memory is part of every savestate this core makes, and 128 MB of it takes space. And a cabinet is something a person built, so a project has to be able to say what it has. A game that reads memory the cabinet does not have reads zeros, as it would from an empty expansion slot.
Panelderived, standard, fighting, lightgun, racing, drum, twinstick, touchderivedHow the cabinet's JVS input wiring is laid out. 'derived' takes it from the Game ID. That is right for every game the board knows, and a project should normally leave it there. The other choices force a layout, for a game that is not in the table or a cabinet that somebody converted. The choice decides which of the Arcade Panel's controls the board actually reads. A fighting cabinet reads six switches and no analog controls, a racing cabinet reads the wheel and the pedals, and a Taiko cabinet reads eight drum sensors. It is part of the machine, so a movie records it. The panel's controls are named after the WIRING and not after any game. 'P1 Button 1' is the first switch on player one's panel, and what it does depends on the game: a punch in one game, a gear change in another. Every control has a default key, so a cabinet can be played as soon as it starts, and you find out what each control does by playing the game. Nothing here is set up for a particular game.
iLink Signature (NAMCO System 246)nonenoneThe regional signature that a System 256 reads from the board's own iLink id. The Taiko Drum Master games use it to decide which region they are in. 'none' leaves the id that the machine's BIOS has. It does nothing on a System 246.
DIP 1: Test Modetrue, falsefalseThe test switch of the input/output board, as on the real board. It is a DIP SWITCH, which is why it is a setting and not a column in the movie. (The cabinet's TEST BUTTON is a separate control, Test in the Arcade Panel, and the board reports the two in one bit.) When the switch is on, the cabinet starts into its own test menu and not into the game. The coin settings, the input test and the game's own options are there. The position of the switch is part of the machine a movie was recorded on.
DIP 2: Video Voltagetrue, falsetrueThe second of the input/output board's four DIP switches. It is reported to the game as part of the board's status. Like the other three it is part of the machine, so a movie records it. The default is the position a cabinet has when it leaves the factory.
DIP 3: Monitor Sync Frequencytrue, falsetrueThe third DIP switch. It says which sync frequency the cabinet's monitor uses, 15 kHz or 31 kHz. It is reported to the game, and some games read it to choose a video mode.
DIP 4: Video Sync Splittrue, falsetrueThe fourth DIP switch. It says whether the cabinet's monitor takes composite sync or separate horizontal and vertical sync. It is reported to the game as part of the same status.
Boot ROM (NAMCO System 256, NAMCO Super System 256)coh-h-256, coh-h-256-mirroredcoh-h-256WHICH arcade board this project is, in the only way the hardware can be told apart. Sony never changed the version or the date in a COH-H ROM: every one says v1.00 (2000-03-06). So the EXTINFO build serial inside the file is what tells them apart, and it names the board. 20021119-163841 is a System 246 Rack C. 20040519-145634 is a System 256 (the Super 256 runs the same ROM with a faster bus clock). 20000901-114731 is the COH-H A-000-010 development board. 'coh-h-256-mirrored' is the same System 256 ROM as a 4 MB file with its two megabytes written twice, which some copying tools produce. It is offered because that file is in circulation, and this core accepts firmware only by its exact hash. A RETAIL PlayStation 2 BIOS does not work and is not offered here. The arcade boot software differs in many module interfaces, and an arcade game does not run on a retail BIOS. The firmware page names the file and the SHA-1 it must have.
Board RAM (NAMCO System 256, NAMCO Super System 256)00How much memory the cabinet has on the NAMCO board, in megabytes. A System 246 Rack A takes expansion boards of 32 or 64 MB in two slots. Racks B and C have 64 MB built in. Wangan Midnight's cabinet has 128. A System 256 has none, and should be set to 0. It is a setting, and is not guessed from the game, for two reasons. The board's memory is part of every savestate this core makes, and 128 MB of it takes space. And a cabinet is something a person built, so a project has to be able to say what it has. A game that reads memory the cabinet does not have reads zeros, as it would from an empty expansion slot.
iLink Signature (NAMCO System 256, NAMCO Super System 256)none, asia4, asia5, japannoneThe regional signature that a System 256 reads from the board's own iLink id. The Taiko Drum Master games use it to decide which region they are in. 'none' leaves the id that the machine's BIOS has. It does nothing on a System 246.

About this data

44 settings, 106 rows. There is one row for each machine and each option. A setting for several machines is repeated for each machine. A setting with no rule is listed under every machine as 'Always shown'. Origin says where the setting came from. 6 machine changes narrow the choices or the default for some machines, and they are applied here.
